# hrva.cc — URL Shortener Frontend

`npm run dev` proxies `/api/v1`, `/oauth2`, `/login` and `/api/changelog` to `http://localhost:8080`, and dev short links (`getShortBaseUrl()`) use the same origin. With the backend stopped, that rewrite answers 500, not the 502 production's gateway gives, so local dev never shows `Reconnecting…` or "Can't reach hrva.cc"; to test a restart locally, point `DEV_API_ORIGIN` at a small proxy that forwards to the backend and answers 502 when the connection is refused. Set `DEV_API_ORIGIN` when starting the dev server to target another backend, e.g. `DEV_API_ORIGIN=http://localhost:18080 npm run dev`; it's read once at startup (`next.config.mjs`), so restart to change it.

No test framework is set up.

`npm run lint` exits 0: the 5 errors that predate CI (`app/connect/content.tsx` twice, `app/fortune/page.tsx`, a `no-explicit-any` in the verify-email resend page, `components/ui/input.tsx`) are listed in `eslint-suppressions.json` (ESLint bulk suppressions), so only a new error fails. Fixing one of them: run `npx eslint . --prune-suppressions` and commit the smaller file. Never add to the file with `--suppress-all` to get a new error through.

`package.json` `overrides` pin `glob` to `^14.0.2` and `minimatch` to `^11.0.1` for every package (Dependabot alerts on `glob` <14.0.2 and `minimatch` <11.0.1), so `npm ls glob minimatch --all` shows one version of each. minimatch 11 has no default export, so an ESLint rule that calls `require("minimatch")` as a function throws (`jsx-a11y/label-has-associated-control` and `control-has-associated-label`, plus some `import/*` and `react/*` rules). None of them is on in `eslint-config-next`; check `npm run lint` after enabling one.

CI (`.github/workflows/check.yml`, on pushes and PRs to `main`): `npm ci`, `npm audit --omit=dev --audit-level=high` (the production dependencies; a high or critical advisory fails the run, the same bar as the backend's OSV-Scanner), on PRs `actions/dependency-review-action` (pinned by SHA like every action, `fail-on-severity: high`, so a PR that adds a dependency with a high or critical advisory fails; needs the dependency graph on), `npx tsc --noEmit`, `npx eslint . --pass-on-unpruned-suppressions` (so a suppression a fix made unused doesn't fail the run), every `check:*` script in `package.json`, and `npm run build`. `codeql.yml` scans `javascript-typescript` (no build) on pushes, PRs and weekly; `.github/dependabot.yml` updates npm and the actions weekly. ## Architecture

### Routing (`app/`)
- `/` - Landing page (public URL shorten + logged-in experience). `app/page.tsx` is a thin server page: it exports the home metadata (`HOME_TITLE`, `HOME_DESCRIPTION`, canonical `/`) and the `/`-only JSON-LD (WebApplication and FAQPage), and renders the client `HomePage` (`components/home/home-page.tsx`). Its "Also included" line names `a warning page before links made without an account that look risky or are being checked`, the only landing mention of the warning page, and (v2.32) `a check of new and changed links for pages that ask for a password or card details`, the landing mention of the sign-in form check. The H1 is `SLOGAN` ("Short links that count clicks, not people.") and the subline under it is the category line ("A free, open-source URL shortener with no ads."). The `<title>` is `HOME_TITLE`: `HOME_TITLE_TEXT` ("Free URL shortener that counts clicks, not people"), a middle dot and the site name. The FAQ text lives in `lib/home-faq.ts` (`HOME_FAQS`, parts with `{ strong }` for bold), so the visible answers and the FAQPage JSON-LD are the same text; there is no microdata. While the public settings say `anonymousLinks` is false and nobody is signed in (`useAnonymousLinksPaused`), `ShortenForm` shows `AnonymousNotice` above the form, its input is `aria-disabled` and read-only, its Shorten button is `aria-disabled` (not `disabled`, so it keeps focus; `handleSubmit` returns early) and the `No account needed. Sign up free` line under the form is hidden. Loading or failed settings, and a sign-in still loading, render the normal form
- `/register`, `/reset-password/[token]` — Auth flows. `/register` has the same **Google** and **GitHub** buttons as `/login` (the shared `ProviderButtons`, `components/auth/provider-buttons.tsx`, with `next` null so they clear `post-login-next`; see `/login` for how the admin's switches change them). When `newSignups` is false (`usePublicSettings`), `/register` keeps the heading and shows `Creating new accounts is paused. Sign in if you already have an account.` (`Sign in` links `/login`) in place of the form, the provider buttons and the terms line. Since v2.23 `/register` answers every sign-up the same way, a new or a taken address (the backend's 202): the form gives way to `Check your inbox at <email> for an email from hrva.cc. It says what to do next.` (wrapped, `role="status"`), a link to `/verify-email/resend` and **Go to sign in**; it never says an account was created. `/reset-password/[token]` asks only for the new password (the token names the account) and posts `{token, password}`; the backend answers 204, and a used or expired link is a 410 whose text is toasted. `/reset-password` says the link works once, for 1 hour. Every new-password field (register, reset, Settings › Change password) is `components/auth/new-password-input.tsx` (`NewPasswordInput`): `autoComplete="new-password"`, a show/hide button (`type="button"`, `aria-pressed`, `aria-controls`, `Show password`/`Hide password`), the rules always under it (`NEW_PASSWORD_RULES`: at least 8 characters, at most 72 bytes, accented letters count as two; `aria-describedby`) and the server's field error under them; there is no confirm field. Current-password fields keep `autoComplete="current-password"`
- Error pages (v2.23): `app/error.tsx` (inside the root layout: logo, theme toggle) and `app/global-error.tsx` (its own `<html>` and `<body>`, imports `globals.css`, applies the stored or system dark theme in an effect, a logo only, no providers) both render `components/error-fallback.tsx`: `Something went wrong`, `This page didn't load. Try again, or go to the home page.`, the error's `digest` as `Reference:` when there is one (wrapped), **Try again** (Next 16's `retry()`) and **Go home**. Both log the error with `console.error`, set a `<title>`, and use no inline handler outside React, so they work under the CSP
- `/login` — Email and password, **Sign in with a passkey** (`components/auth/passkey-sign-in-button.tsx`, with a **How passkeys work** link under it) and passkey autofill from the Email field (`usePasskeyAutofill`: only while the tab is visible, it runs again when the tab comes back, and never again after a sign-in succeeds). A two-step account gets the shared `SecondStep` screen (`components/auth/second-step.tsx`) with the methods from the login response: **Use a passkey or security key** for `WEBAUTHN`, then **or enter a code** and the code field for `TOTP` / `RECOVERY_CODE` (trimmed before sending; the backend ignores case, spaces and a missing dash). Under it, **Use a different account** returns to the password form with the email kept (password cleared) and **Lost your passkey or codes?** opens `/help/passkeys#lost-device` in a new tab. A 410 returns to the form with the backend's text as the toast (expired, or out of tries), except an expired passkey request from the verify call (`This request expired. Try again.`): that stays on the step, shown under the passkey button, and the next press fetches fresh options. 401, 403 and 400 texts (tries left, account and network locks) are shown as the backend sends them; the browser-side wrong-key text is only for `NotAllowedError`. `?next=` (checked by `safeNext`) is where a sign-in lands; the **Google** and **GitHub** buttons (side by side under "Or continue with", outline buttons linking to `/oauth2/authorization/google` and `/github`) keep it in `sessionStorage` (`post-login-next`) for the callback. Since v2.27 the links carry a challenge: on mount `ProviderButtons` prepares one verifier and its S256 challenge (`prepareSignInChallenge` in `lib/oauth-challenge.ts`: 32 bytes from `crypto.getRandomValues`, base64url) and both hrefs become `/oauth2/authorization/{provider}?challenge=…`, so the code that comes back only works in this browser (the backend refuses a start without a challenge with `?error=provider_error`). The verifier is written only when the link is used, on `click`, `auxclick` (middle-click) and `contextmenu` (open in a new tab or window): `keepSignInVerifier` puts `{verifier, expiresAt}` (10 minutes) in one `localStorage` slot, `oauth-verifier`, overwritten by each start, every access in try/catch. `localStorage` rather than `sessionStorage` (v2.27, owner call) so middle-click and open-in-new-tab work: the threat is a code reaching another browser, and every tab of this one shares the slot. Until the challenge is ready (a moment after mount; never on an origin without Web Crypto) the buttons have no href, are `aria-disabled` and ignore clicks, so an early click can't start a sign-in that would fail. There is no other place that starts a Google or GitHub sign-in (Settings only turns methods on and off), so `/login`, `/register` and the MCP `/connect` bridge (through `/login?next=`) are all covered by `ProviderButtons`. `ProviderButtons` follows the admin's site-wide switches from `usePublicSettings`: the Google button renders unless `googleSignIn === false` and the GitHub button unless `githubSignIn === false`, so they show while the settings load or fail and hide only on an explicit `false`. One hidden button leaves the other full width (`grid-cols-1`); with both hidden the "Or continue with" divider goes too. On `/login` only (`explainOff`), a muted line under the buttons says `Sign in with Google is turned off right now. No password yet? Use Forgot password to set one.` (`Signing in with Google and GitHub is turned off right now.` when both are off; `Forgot password` links `/reset-password`), so a Google- or GitHub-only account is pointed at Forgot password and never at "your email and password". The public pages stay static (`○`); the buttons and the line are client-side
- `/auth/callback` — Where Google and GitHub sign-ins come back: `?code=` (v2.22; the backend never puts the token in the URL) is removed from the address bar (`replaceState` in a layout effect), any stored token is dropped, and the code is posted once to `POST /auth/oauth/exchange` with the tab's verifier (`authApi.exchangeOAuthCode(code, verifier)`, v2.27; `takeSignInVerifier` reads and removes the `localStorage` `oauth-verifier` slot on every visit to the page, success or error, and treats an expired or unreadable value as none; without one the page shows `provider_error`'s text without posting; a ref keeps StrictMode's second effect from spending the code twice), whose answer signs in like `/login` (`completeSignIn`, then the `post-login-next` path, so `/connect` and `next` still work) or, if two-step was turned on meanwhile, shows `SecondStep`; a 410 shows `SIGN_IN_EXPIRED`. A two-step account gets the same `?code=`; the exchange answers `pendingToken` and `methods` and the page shows `SecondStep`. There is no `?token=` or `?pendingToken=` handling any more (v2.22: the backend never puts a token of any kind in a URL; the old branch went with it, since a v2.21 backend's `?token=` redirect wouldn't work with this page either, so backend and FE ship together). The page is answered with `Referrer-Policy: no-referrer` and `Cache-Control: no-store` (`withCallbackHeaders` in `lib/security-headers.ts` from the worker, and `public/_headers` for a static copy). Its way out is **Back to sign in** (`/login`): a button when there's no code field, a link under the form otherwise. A 410 shows the backend's text on the error card; `?error=` (`no_email`, `account_inactive`, `sign_in_unavailable` (Redis down for the one-time code: `Signing in isn't available right now. Try again in a minute.`), `invalid_email`, `github_email_unverified`, `google_email_unverified`, `registration_disabled`, `provider_error`, `provider_turned_off`, `provider_disabled`) shows its message, any other code "Authentication failed." GitHub sign-ins use the account's verified primary email; `github_email_unverified` ("Your GitHub account has no verified email address. Verify one on GitHub, or sign in another way.") and `google_email_unverified` ("Your Google account's email address isn't verified.") are the backend refusing an unverified address, and `registration_disabled` shows `Creating new accounts is paused. Sign in if you already have an account.` (`SIGNUPS_PAUSED` plus the `/register` sentence, so the callback and `/register` say the same), when new sign-ups are paused and the Google or GitHub account has no hrva.cc account yet. `provider_error` ("Signing in didn't work. Try again, or sign in another way.") is any other failure of the Google or GitHub flow, such as a cancelled consent. `provider_turned_off` is the backend refusing a provider the account turned off in Settings (`{Provider} sign-in is turned off for this account. Turn it back on in Settings after signing in another way.`); the redirect carries `&provider=GOOGLE|GITHUB`, which the callback prefers (`providerFromParam`); without it (or with another value) it falls back to the provider `/login` and `/register` wrote to `sessionStorage` on click (`oauth-provider`, `rememberOAuthProvider` in `lib/sign-in-methods.ts`), cleared by the callback. `provider_disabled` is the site-wide switch (v2.20): `{Provider} sign-in is turned off on hrva.cc right now. Sign in with your password or a passkey. No password yet? Use Forgot password to set one.` (`providerDisabledText`, under the heading `{Provider} sign-in is off` (`providerDisabledHeading`) with `Forgot password` linking `/reset-password` and the button **Back to sign in**; the redirect carries `&provider=GOOGLE|GITHUB`, read like `provider_turned_off`'s, and without one it starts `That sign-in`); it never mentions email and password, because an account made through Google or GitHub has no password. With neither, the `provider_turned_off` text starts `That sign-in is turned off`

### API Client (`lib/api-client.ts`)
- `request<T>(method, path, body?, headers?)` — fetch wrapper with auth token injection
- Reads `localStorage.getItem("auth-token")` and sends it as-is in the `Authorization` header. The stored value already starts with `Bearer ` (every sign-in answer's `token`, the OAuth code exchange's included)
- **Renewed tokens** (v2.22): a successful answer with an `Authorization` response header (the backend exposes it through CORS) replaces the stored token, but only while the stored one is still the token the request sent. A password change, removing the password, turning Google or GitHub off and Sign out everywhere end every other session and send this device a new token that way; `userApi.endAllSessions()` (`POST /users/me/sessions/end`) also stores the body's `token`
- **Session ended** (v2.22): a 401 whose message is `SESSION_ENDED` (`Your session ended. Sign in again.`), for the token still stored, removes it and calls the listener `AuthProvider` registers with `onSessionEnded`, which signs out (`endSession(null)`, so the layouts send the user to `/login?next=…`) and toasts that text once (id `session-ended`); `showSessionEndedOnce` (`lib/session-ended-toast.ts`, installed by the auth context) gives any other `toast.error` of that text the same id, so a page that also toasts the failed call doesn't show it twice. Other 401s change nothing. The three downloads (`urlApi.exportCsv`, `userApi.exportMyData`, `adminApi.exportUrlsCsv`) go through `download()`, which does the same, keeps a renewed token and throws an `ApiError` with the problem's `detail` (checked by `npm run check:api-client`)
- **Visit limits** (v2.23): `UrlResponse.opens` is how many clicks counted towards `visitLimit` (every click, not bots or HEAD; the backend counts it before the redirect, and `visits` stays daily unique visitors). `opensText(link)` in `lib/utils.ts` (`3 of 5 clicks used`) is shown under the visits on the dashboard (with a progress bar on `opens`) and in the admin URLs list and status line; `VISIT_LIMIT_HINT` (`Every click counts, not counting bots.`) sits under the visit limit field of the home form, the dashboard's create dialog and the admin edit dialog (`aria-describedby`); the home FAQ and `/developers` say the same (checked by `npm run check:api-client`)
- **Created links** (v2.23): `POST /urls` answers 201 with `shortLink`, the full short link (`https://hrva.cc/<alias>` or `https://<hostname>/<alias>`); `request()` treats it like any `ok` answer. `shortLinkOf(link)` in `lib/utils.ts` prefers `shortLink` and falls back to `formatShortUrl(shortUrl, domain?.hostname)` for answers without it; the shorten form, the UTM builder, the QR generator and the dashboard's create dialog show and copy it (checked by `npm run check:api-client`)
- A 429 without a message reads `Too many attempts. Try again in a few minutes.`; the backend's sign-in 429 carries its own (`Too many sign-in attempts. Try again in N minutes.`), which `/login` toasts
- `ApiError` class exposes `.status`, `.message` and (v2.27) `.problem`, every member of the problem body, so extension members such as the edit's `missing` and `verdict` reach the form; `REQUEST_FAILED` is the fallback message when a 4xx body has none. A network failure (`fetch` throws; status `0`) or a 5xx without a JSON message (the dev proxy, a Cloudflare error page) gives `CANT_REACH`, "Can't reach hrva.cc right now. Check your connection and try again."; a 5xx problem with a `detail` (the Redis-down 503s) keeps its text
- `request()` reads JSON or plain-text bodies (202 and 204 answers resolve to `{}`, so `authApi.register` and `authApi.resetPassword` return nothing); every error is an RFC 9457 problem (`application/problem+json`, v2.22): `errorMessage(body, status)` takes `detail`, else `title`, else the fallback
- Signing in or out clears the React Query cache; a failed `/users/me` only drops the token on 401/403
- **Retries, restarts and outages** (`lib/api-client.ts`, checked by `npm run check:api-client`): `isRestartError` is a network failure, a 502, 504, or a 503 that isn't a database outage. `isOutage` (v2.31) is a 503 whose problem has a string `outage` member (`"database"`, or `"cache"` when Redis is down: `hrva.cc can't reach its cache right now. Try again in a minute.`) or, from a v2.30 backend, the exact `detail` `DATABASE_UNREACHABLE` (`hrva.cc can't reach its database right now. Try again in a minute.`): the server is up and says so, its text is shown as sent, so it is never retried (`shouldRetry` and `retryUnlessRefused` answer false) and never shows `Reconnecting…`. A restart is retried with `retryDelay` (1, 2, 4, then 8 s) for `RESTART_RETRY_WINDOW_MS` (120 s) of wall-clock time, request time included, timed per retry chain (v2.31, `shouldRetryFrom(chainStartedAt, failureCount, error)`): every query's `retry` function is wrapped by `perQueryRetry(queryHash, retry)` (`timeRetriesPerQuery` in `lib/query-client.ts`, patched onto the client's `defaultQueryOptions` in `app/providers.tsx`), so a query's window starts at its own first failure and a query that starts failing late in a long outage still gets its 2 minutes, while each chain stays bounded; outside a query, a chain starts at each `failureCount` 0; `fetchMeThroughRestart` times its own. Separately, the outage itself is timed from when the backend first stopped answering: `request()` and `download()` note it (`noteBackendFailed(startedAt)`, the time the failing request was sent; `backendRestartingSince()`), and only an answer clears it. The notice (`reconnectingState(now)`) shows while anything retries a restart: `Reconnecting…` while that outage is younger than the window, then `Can't reach hrva.cc right now. Still trying…` (`STILL_TRYING_TEXT`) while pages still retry after it (a query that started failing late keeps its own 2 minutes), and it goes when nothing retries any more. It also stays hidden while a full-page notice already says hrva.cc can't be reached: `ServiceUnavailable` and the Health page's error state register themselves while on screen (`useFullPageNotice`, a counter in `lib/reconnecting.ts`), so each screen shows one message. The text switches on a timer set once per outage start (`notifyWhenTheWindowEnds`), so a second outage while the same queries retry gets its own. ### Auth (`lib/auth-context.tsx`)
- React Context provider wrapping the tree under `Providers`
- On mount: reads `auth-token` from localStorage, calls `GET /users/me` to hydrate user (through a restart with `fetchMeThroughRestart`, under the `Reconnecting…` notice)
- `unavailable` (v2.31): when `/users/me` fails with anything but a 401 or 403 (an outage at once, a restart after its 120 s), the token stays and `unavailable` holds the error's text (`CANT_REACH` when it has none); while it is set and there is no user, `recheck` runs `refreshUser` every 30 s (`UNAVAILABLE_RECHECK_MS`) and when the backend is announced back, skipping a tick while one is still running (the `checking` ref), so a long restart never stacks retry chains. A success, a sign-in or a sign-out clears it
- **Rolling sign-in** (v2.31): while signed in, a `pointerdown` or `keydown` renews the session (`userApi.renewSession()`, `POST /users/me/sessions/renew`, the new token kept by `keepRenewedToken`) when `dueForRenewal(lastRenewedAt, now)`: at once on the first activity in a tab, then at most every 5 minutes (`RENEW_EVERY_MS`). Polling alone never renews, so a page left open still ends 10 hours after the last activity; the backend never extends a sign-in past 30 days
- A 401 or 403 from `/users/me` (v2.31, `answerToRefusal` in `lib/session-check.ts`, checked by `npm run check:session-check`): the `SESSION_ENDED` 401, a token whose `exp` has passed (`tokenExpired` reads the JWT payload without checking the signature; an unreadable token counts as expired) or a second refusal in a row signs out as before. The first refusal of a token that hasn't expired keeps the token, sets `unavailable` to `COULDNT_CHECK_SIGN_IN` (`hrva.cc couldn't check your sign-in.`, not the refusal's own text, which would contradict "You haven't been signed out") and waits for the 30-second recheck. `completeSignIn` and `endSession` reset the refusal count, so a new sign-in starts with a clean slate. No token in storage (another tab signed out) still goes to the sign-in page
- `login()` returns a `LoginResult`: `{ status: "signed-in" }` (token stored, user set) or `{ status: "two-step", pendingToken, methods }`. `completeSignIn(signedIn)` stores the token and user for every other way in (passkey, second step, callback)
- `logout()` removes the token, clears the query cache and the user, and dismisses the `Sign in again` toast (`REAUTH_TOAST_ID`). A session ended elsewhere (the `SESSION_ENDED` 401) signs out the same way, with that text in a toast. `logoutTo(destination)` does the same and sends the dashboard and admin layouts (and `ProtectedRoute`) to `destination` instead of the sign-in page with `next` (account deletion → `/login`)
- Unavailable rather than signed out (v2.31): the dashboard layout and `ProtectedRoute` show `ServiceUnavailable` (`components/service-unavailable.tsx`: the backend's text, `You haven't been signed out. This page tries again every 30 seconds.` (the token couldn't be checked) and a Retry button that calls `refreshUser`) instead of the sign-in page. The admin layout keeps its nav and sidebar and shows the same notice, except on `/admin/health`, which renders the Health page so its own 503 state gives the database sentence; nothing redirects while `unavailable` is set and there is no user. So during an outage the admin shell renders on `/admin/health` for anyone holding a token: the role can't be checked without the database, and no data is served
- Signed out on a dashboard or admin page (or inside `ProtectedRoute`) → `router.replace("/login?next=" + encodeURIComponent(pathname + search))`, so signing in returns to the same page, query included (a link to `/admin/urls?search=<domain>` opens with the search filled in), and Back doesn't loop. A signed-in non-admin on an admin page is still pushed to `/dashboard`
- `useReauthToast()`: a 401 for an account that confirms by recent sign-in (Google or GitHub, or an email account whose password was removed; see `useNeedsPassword()`) shows one persistent `Sign in again` toast (id `REAUTH_TOAST_ID`) with the backend's text (passkey add and remove, account deletion); its action is `logout()`
- `isAdmin` derived from `user.authorities` containing `{ name: "ROLE_ADMIN" }`
- **No route protection middleware** — dashboard/admin layouts redirect client-side via `useEffect`
- `components/protected-route.tsx` (`ProtectedRoute`) has no importer: the dashboard and admin layouts do the same check themselves. It follows the same redirect rule so it stays safe if used again; remove it when convenient

On submit with the check active the form waits up to `HUMAN_CHECK_WAIT_MS` for a token (button text `Checking` plus U+2026, from `String.fromCodePoint`, with the button `aria-disabled` and `aria-busy` rather than `disabled`, so focus stays on it; `ShortenForm`'s button is also `aria-disabled` + `aria-busy` while the create is pending, never `disabled`, and `handleSubmit` returns while `createUrl.isPending`, so focus stays on Shorten after a 400, 429, 503 or network error), sends it as `X-Turnstile-Token`, and calls `reset()` after every attempt, success or failure (tokens are single-use). A token older than `TURNSTILE_TOKEN_MAX_AGE_MS` (290 s, `freshTurnstileToken`; a throttled background tab can miss Cloudflare's own refresh) is never sent: `waitForToken` resets the widget and waits for a fresh one. While the visitor is shown the box to tick (`before-interactive-callback` until `after-interactive-callback` or a token), `waitForToken` doesn't time out or reset: the button stays `Checking` plus U+2026, a muted `TICK_THE_BOX` (`Tick the box above to continue.`, `role="status"`) shows under the box, and the create is sent as soon as the token arrives. Otherwise no token in time calls `reset()`, so a widget stuck in an error state starts over on the next press; no token in time, or the backend's same refusal, shows an alert under the field or button until the next attempt: `Complete the check and try again.` when the visitor was shown the box (`boxShown` in the state), or when the page had no check to run (the backend's 400 for a page that never sent a token, which also triggers the settings refresh), and `The check couldn't confirm you're a person. The backend's 503 `We couldn't run the check. There is no CSP (`public/_headers` sets only cache headers, `next.config.mjs` none), `lib/junk-paths.ts` only sees same-origin paths, and `sw.js` handles only same-origin navigations, so nothing blocks the cross-origin script or iframe. **Browser storage (R65, measured 2026-10-30 in Chromium with the always-pass test key `1x00000000000000000000AA`):** after a check, no cookies on any origin, nothing in hrva.cc's own `localStorage`, `sessionStorage`, IndexedDB or cache storage; the Turnstile iframe (`challenges.cloudflare.com`, partitioned under the top-level site) writes one `localStorage` key, `cf.turnstile.u` (a 106-character opaque value). A candidate runs to whitespace, `<`, `>`, a double quote or a backtick; trailing `. , ; : ! ? '`, closing curly quotes, the right guillemet and the ellipsis are dropped, and a closing `)`, `]` or `}` only when unbalanced (so Wikipedia's `..._(band)` survives). Navigations go to the network (the preload response when there is one) and get the cached `/offline` only when the fetch rejects, never on a 4xx or 5xx. ### Deployment (Cloudflare Workers)
- Built with `@opennextjs/cloudflare` — config at `open-next.config.ts` (the read-only static-assets incremental cache, so no ISR revalidation)
- `wrangler.jsonc`: name `url-shortener`, `nodejs_compat` flag, assets from `.open-next/assets`, `main` is `custom-worker.mjs` (OpenNext's custom worker: it first answers junk paths with a plain 404 (`junkPathResponse` in `lib/junk-paths.ts`, below), then re-exports `.open-next/worker.js`'s `fetch` through the bio edge cache; plain JS because the generated import only exists after `npm run build:cf`; a Durable Object class added later, such as OpenNext's `DOQueueHandler`, must be re-exported from it), and the `CF_VERSION_METADATA` version metadata binding (not a resource, nothing to create)
- **Sign-in callback headers** (`withCallbackHeaders`, checked by `npm run check:worker`, v2.22): `/auth/callback` (with or without a trailing slash, any query) gets `Referrer-Policy: no-referrer` and `Cache-Control: no-store` from the worker, replacing Next's `s-maxage`; `public/_headers` sets the same on `/auth/callback`.
- **Content security policy** (`lib/security-headers.ts`, checked by `npm run check:worker`, v2.22): `custom-worker.mjs` adds `CONTENT_SECURITY_POLICY` to every `text/html` answer from Next (`withContentSecurityPolicy`, after the bio edge cache, so cached bio pages get it too), and `public/_headers` puts the same policy on every static file the assets serve (`/*`); the check fails when the two differ. A header, not a nonce, so the public pages stay static. Sources: `default-src 'self'`; `script-src 'self' 'unsafe-inline' https://challenges.cloudflare.com` (Next's inline RSC payload and bootstrap scripts, next-themes' inline theme script, and the Turnstile script); `style-src 'self' 'unsafe-inline'` (React `style` attributes, Recharts and Radix inline styles); `img-src 'self' data: blob: https:` (`data:` images such as QR downloads, `blob:` for the link inspection screenshots, which are shown from object URLs, and link preview images from any https site); `connect-src 'self' https://hrva.cc` (the API, `/api/changelog` and the bio view beacon; dev uses the same-origin proxy); `frame-src https://challenges.cloudflare.com` (the Turnstile widget); `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, `object-src 'none'`. A browser run of every route on the built Worker (Playwright, the API mocked, Turnstile's test site key `1x00000000000000000000AA`, a bio page and its share image) found no violation. A Cloudflare dashboard feature that injects a script (Web Analytics beacon, Rocket Loader, email obfuscation) would need its host added here first.
- **Stale chunks after a deploy** (v2.25, `lib/stale-chunk.ts`, `components/stale-chunk-reload.tsx`, checked by `npm run check:stale-chunk`): a tab opened before a deploy still runs the old build, and its old `/_next/static/*` chunks now answer the Worker's plain 404 (see Junk paths), so a navigation that needs one would fail. When the app fails to load one of its own chunks, it reloads the page once (`window.location.reload()`, which fetches the new build). Detection: `StaleChunkReload` (a client component in the root layout, no inline script) listens for `error` in the capture phase (a `<script>`, or a `<link rel="stylesheet">`, whose URL is same-origin and under `/_next/static/`; skipped while a form field or editable element has focus, so a background prefetch never throws away typing) and for `unhandledrejection`; `app/error.tsx`, `app/global-error.tsx`, `app/bio/[handle]/error.tsx` and the react-query `QueryCache` and `MutationCache` `onError` (never for an `ApiError`) call `reloadIfStaleChunkError`, which matches an error named `ChunkLoadError` (Turbopack's `Failed to load chunk static/chunks/... from module N`, with no URL or an own one), and a CSS chunk or dynamic-import failure (Chrome's `Failed to fetch dynamically imported module`, Firefox's `error loading dynamically imported module`, Safari's `Importing a module script failed.`) only when its message names an own `/_next/static/` URL, through `cause` too, and never a message naming another site's URL (Turnstile). Guard: `sessionStorage` `hrva:stale-chunk-reload` holds `{path, at}`; another failure on the same pathname within 30 s shows the normal error UI instead of reloading, and blocked storage, storage that doesn't read back what was written, or `navigator.onLine === false` (the offline page and the error UI stay) means no reload at all, so it can never loop. After a deploy the reload is usually of the page the visitor was on, not the one they clicked (the address bar hasn't changed yet), so a navigation that failed on a stale chunk needs a second click once the new build has loaded. No FE `queryFn` imports code (every query is a `fetch` to the API), so a query's error state is never a chunk failure; the query cache hook is a safety net. Next itself already does a full navigation when a non-prefetched route's answer comes from a newer build, and prefetching loads a route's chunks along with its data, so the reload covers what is left: a chunk the old page asks for after the deploy
- **Junk paths** (`lib/junk-paths.ts`, checked by `npm run check:worker`): a request that no asset and no route can answer would otherwise run the whole Next server and render `not-found` (85-365 ms of CPU on the free plan's 10 ms budget), so `custom-worker.mjs` answers these with `404`, `text/plain`, body `Not found`, `Cache-Control: public, max-age=600` (`no-store` for `/_next/static/*`, so a deploy that is still spreading can't pin a 404 for a chunk that exists a moment later) before the bio cache and Next, for any method: any `/_next/static/*` (real files are served by the assets before the Worker, so a request that reaches it is a stale chunk from an older build), `/wp-*`, `/cgi-bin/*`, `/phpmyadmin*`, any path segment starting with a dot (`/.env*`, `/.git*`, `/.aws/*`), and a path ending in `.php`, `.phtml`, `.asp`, `.aspx`, `.jsp`, `.cgi`, `.env`, `.sql`, `.bak`, `.zip`, `.tar`, `.gz`, `.rar`, `.7z`, `.ini`, `.log`, `.yml`, `.yaml` or `.pdf`. Never intercepted: `/robots.txt`, `/sitemap.xml`, `/manifest.webmanifest`, `/llms.txt`, `/favicon.ico`, `/sw.js`, `/.well-known/*`, `/_next/image`, and every route. Only the path decides (not the query), and percent-encoded dots are not decoded, so `/%2eenv` still reaches Next. Add a new real route or file with a dot to the check's `passed` list first
- Footer links (`components/site-footer.tsx`) have `prefetch={false}`: the footer is on every page with about 19 internal links, and each one scrolled into view fired a Worker request (`_rsc=` was 52% of all invocations). The header's links still prefetch
- Only `/bio/[handle]` and its share image are edge-cached (see Bio pages); the other dynamic routes (`/protected/[short]`, `/reset-password/[token]`, `/validate/[short]`, `/verify-email/[token]`) render on every request as before, and the rest is static
